# Coder ワークスペースの起動遅延（2026-11-04）

## 影響

`dYdx` と `CKB-VM` は Coder 上で起動中と表示された一方、ワークスペースエージェントが接続できず、開発環境として利用できなかった。2 件の直接原因は異なる。

## 原因と復旧

* `dYdx`: 実行中のテンプレートバージョンが、以前のレジストリ初期化で失われた古いイメージのダイジェストを参照していた。既存ワークスペースはテンプレートの自動更新が無効で、イメージが復旧した新しいバージョンを自動的に使用していなかった。更新済みテンプレートで起動し、既存の永続ディスクを維持したままエージェントの接続を確認した。
* `CKB-VM`: 永続ディスクを 2 台に複製する際、ストレージノード `uc-k8sp5` の空き容量が 25% の予約領域を維持する条件を満たせず、ディスク作成が保留になっていた。古いシステムログを圧縮・退避して空きを確保した後、2 コピーが作成され、エージェントの接続を確認した。ユーザーのディスクは削除していない。

両ケースで、Coder の構築完了は Flash への作成要求が受理された時点で判断され、実際のコンテナや永続ディスクの準備が完了していないことが利用者に伝わりにくかった。

## 再発防止

* Flash の現在の世代が準備完了になり、レプリカが起動するまで Coder の構築を待機する。イメージ不在や複製先の容量不足などは構築ログに理由を表示し、待機がタイムアウトした場合も失敗として表示する。停止操作では待機しない。
* Standard と Big の両テンプレートに反映した。既存の `dYdx`、`CKB-VM`、`ramen` は次回起動時に現行テンプレートを使う設定に変更した。今回の設定変更に伴う稼働中ワークスペースの再起動は行っていない。
* Big テンプレートは実際には 8 vCPU を要求していたが、Coder の表示は 4 vCPU だった。表示を実際の要求値から生成する。
* ホストのシステムログをサイズ・期間でローテーションし圧縮する設定と、journal の上限を Terraform / Ansible で管理し、利用可能な 5 台に適用した。今回退避したログのアーカイブは保持している。

## 検証

* 変更済み Standard テンプレートで一時ワークスペースを実際に作成し、Flash イメージの取得、永続ディスクの 2 コピー、エージェントの接続を確認した。Chromium で VS Code のファイル表示、双方向 WebSocket、および再読み込みを確認した。検証用ワークスペースとストレージはすべて削除した。
* イメージ不在・容量不足・古い世代を含む待機処理の自動テストを実行した。[HeteroCloud の CI](https://github.com/IPA-CyberLab/IPA-RS-HeteroCloud/actions/runs/41796572969) と [HeteroNetwork の CI](https://github.com/IPA-CyberLab/IPA-RS-HeteroNetwork/actions/runs/41797556910) が成功した。

## 残る注意点

`dYdx` の `/root` は調査時に 26 GiB 中 25 GiB を使用しており、空きは約 1.4 GiB（使用率 95%）だった。ログのローテーションはホスト側の空き容量を保つための対策であり、このワークスペースのデータ容量を拡張するものではない。停止中のストレージノード `uc-k8sp4` を除くと複製先に使用できるノードは 2 台で、引き続き容量と冗長性に注意が必要。
