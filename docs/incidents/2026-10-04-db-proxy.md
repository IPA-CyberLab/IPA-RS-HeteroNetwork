# 2026-10-04: intermittent database connection termination

Status: proxy fix deployed and sustained recovery checks passed on 2026-10-04.
Final public API/exec verification completed at **11:01:24**. Times are UTC.

This is part of the [Flash update/exec incident](https://github.com/IPA-CyberLab/IPA-RS-HeteroCloud-Flash/blob/master/docs/incidents/2026-10-04-flash-update-exec.md).
The PVC update failure and diagnostic generation gate are separate Flash defects.

## Impact and cause

At **10:11:50.396701**, the database proxy on `ichikawap1` marked backend `db-e`
DOWN after its `/primary` check returned 503. Its configured
`on-marked-down shutdown-sessions` behavior terminated 18 active sessions.
HeteroCloud's API logged TLS EOF and HTTP 500 at **10:11:50.403**.

Both database members had **two HAProxy frontends listening on the identical
overlay address and TCP port 18008**. One forwarded to the current primary;
the other forwarded to that particular member's Patroni endpoint. HAProxy's
reusable listeners accepted both binds, so a replica's overlay health port
randomly answered with either 200 (the primary) or 503 (the local replica).
The downstream proxy mistakenly interpreted this as backend failure and closed
healthy database connections. There was no primary PostgreSQL process restart
at this time; the postmaster start time was 2026-10-01.

Before correction, 20 certificate-verified requests from `ichikawap1` observed:

| Overlay endpoint | HTTP 200 | HTTP 503 |
| --- | ---: | ---: |
| `10.250.0.2:18008/primary` | 20 | 0 |
| `10.250.0.11:18008/primary` | 7 | 13 |

`ss -ltnp` independently showed two listening sockets for each member's overlay
health address. The generated config named the conflicting frontends
`heteronetwork_postgres_overlay_health` and `heteronetwork_patroni_health`.

## Why reconciliation did not repair it

The renderer emitted both frontends when `client_listen_address` equaled
`proxy_listen_address`, which is the deployed member configuration. Existing
renderer tests used *different* addresses, and the drift check only tested for
the presence of a matching bind, not uniqueness.

The proxy-only autopilot also rejected the recovered topology: it required at
least three PostgreSQL members and required every DCS voter to be a PostgreSQL
member. The real topology intentionally has two synchronous PostgreSQL members
and three DCS voters, including a dedicated DCS node. The node helper already
supported this configuration; proxy validation and backend mapping did not.
This produced recurring `invalid database member count` errors.

## Changes and validation

- Render one primary-health frontend when the two listen addresses coincide.
  Keep a distinct local-member health endpoint only when its address differs.
- Check that overlay health has exactly one generated listener.
- Accept two PostgreSQL members with a separate three-or-more, odd-sized DCS
  quorum in proxy bundles; retain identity/address consistency, private-file,
  CA, and allowed-file validation. Map two member backends correctly.
- Add regression cases for shared and distinct listener addresses, the recovered
  two-database/three-voter topology, and invalid DCS/address combinations.
- Add `terraform_data.database_proxy_configuration` and its Ansible playbook.
  They validate and atomically install the config, gracefully reload HAProxy,
  update the proxy-only client's reconciler, and require 30 consecutive verified
  `/primary` successes per node. Database processes and application containers
  are outside this resource's restart scope.
- Include this resource in the operator wrapper's drift checks. Its playbook is
  excluded from the master host bundle hash, so it does not trigger master
  reprovisioning.

Both database shell self-tests passed. Terraform formatting and validation, and
Ansible syntax validation passed. The targeted incident plan changes only the
proxy resource; it does not assert that unrelated infrastructure drift is absent.

## Live recovery record

Terraform applied source revisions `8244ff0a` and `4936a4c0` successfully to
`uc-k8sp4`, `uc-k8sp5`, and `ichikawap1`. All three passed 30 consecutive verified
health requests. The first apply stopped at its acceptance gate while HAProxy's
new worker was still establishing backend health. The gate now permits bounded
startup retries and still requires a complete run of 30 successes; the second
apply completed. No database process or application container restart was
requested.

The replaced Terraform object was a `terraform_data` provisioner record, not a
database, VM, Pod, or volume. After correction, both overlay endpoints returned
**30/30 HTTP 200** from `ichikawap1`; the inspected post-change proxy/autopilot
logs had no backend-down or invalid-bundle events. A single connection through
that node's local database proxy completed **180 queries over 370.176 seconds**
(10:48:57–10:55:07), with no errors and the same session throughout. The primary
postmaster start time remained **2026-10-01T06:03:42.238246Z**, confirming no
primary PostgreSQL process restart.

All three HeteroCloud API replicas were inspected from 10:48 through 11:01:
there were zero matching TLS EOF, database connection, or container-diagnostic
failure log lines. This is a bounded observation window, not an assertion that
every possible error was absent.
