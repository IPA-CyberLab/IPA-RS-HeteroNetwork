# Runtime restart acceptance, 2026-10-17

The operator authorized a bounded stop and restart for security patches. CPU sandbox updates preserve persistent disks and configuration; they reset process memory and established connections.

## Findings and corrections

- A native 20261005.0 → 20261012.0 canary recovered in 17.922 seconds with its original PVC and file marker. A dependency returning HTTP 503 caused restoration and verified recovery of the previous complete runtime bundle. Final target acceptance completed at 09:08 UTC.
- A legacy Flash secret initializer had no memory limit. The application limit alone left Sentry inside the node's much larger Pod memory boundary. An isolated native reproduction measured 29,262,143,488 bytes before repair and 134,217,728 bytes afterward, retaining its file marker. Replacement took 18.120 seconds. Updating `/resize` metadata and restarting the same Pod does not invalidate kubelet's cached nonrestartable initializer allocation.
- The Flash helper now requests 16 MiB with a 64 MiB memory limit. IaC declares admission defaults, and existing helper resources are repaired without an additional application restart. Legacy Pods are then replaced using an API eviction and a scheduling gate, releasing the new Pod only after the original Sentry is fenced. The corrected Deployment template and PVC identities remain unchanged by replacement.
- At 09:35 UTC an existing 8 GiB workspace encountered a Longhorn remount deadlock: four old Failed Pod objects still referred to its PVC. Removing only those terminal objects allowed its new container to start at 09:37:26 UTC. The PVC, volume, engine and replicas were not modified. Another retained Failed workspace Pod was removed before its disk remount. This matches [Longhorn issue 13723](https://github.com/longhorn/longhorn/issues/13723). Storage preflight now rejects these references before any stop, including references still cached in Longhorn.
- The following workspace's CRI StopPodSandbox acknowledgment exceeded the client's 30-second timeout. The controller held the update and restored the previous complete bundle. That worker's previous runtime was 20260817.0, older than the original activation allowlist, which prevented reporting verified recovery through the restricted endpoint even though the workspace recovered. Inspection now reports installed runtime identities after a rollback; recovery may use only the protected previous bundle. The timer still requires the declared target version and cannot downgrade healthy target sandboxes.
- A late stop acknowledgment is now recorded as pending, without repeating the stop. Acceptance still requires source process fencing and full recovery within 180 seconds. A regression test verifies both the pending result and the retained single-attempt budget.
- Kubernetes status updates caused a metadata resourceVersion precondition to reject an otherwise unchanged Deployment during an isolated repair test. Configuration writes now compare the exact UID, spec, annotations, labels and owning references, permitting status-only updates while rejecting concurrent configuration changes.

## Acceptance and evidence

`gvisor-restart-e2e.yml` uses a real disposable Kubernetes/containerd node. Native verification also uses the actual restricted SSH endpoint and Longhorn volumes. The initializer test creates its own real Failed Pod sharing the test disk, verifies that preflight refuses the stop, cleans up the test record, and then checks repair, fencing, memory enforcement and persistent data.

Private evidence is kept under `/workspace/.heteronetwork-iac/security-20261017` and `/var/lib/heteronetwork-security` on the operator. It contains runtime hashes, Pod/PVC identities, acceptance results and the reviewed prior attempt; application environments, secret values and user files are not collected. Successful canary evidence is written only after cleanup. Automatic timers cannot clear a held candidate or its restart budget.
