# DEV Application Databases

## Implementation

`databases.py` uses the shared release-environment `app_postgres.py` renderer
with the observed DEV cluster's addresses, app StorageClass and the same
digest-pinned PostgreSQL image already validated by the identity foundation.
It generates three independent CNPG clusters, not copies of identity data.

| Namespace | Database And Owner | Instances | Storage Per Instance |
| --- | --- | --- | --- |
| heterocloud-dev | heterocloud_dev | 3 | 5Gi |
| heterocloud-flow-dev | heterocloud_flow_dev | 3 | 5Gi |
| heterocloud-syouyu-dev | heterocloud_syouyu_dev | 3 | 5Gi |

Each cluster is named `dev-postgres`, requires hostname anti-affinity, and uses
`ANY 1` synchronous replication with required data durability and failover
quorum. Credentials are generated by CNPG; no existing Secret or database is
imported. Non-root UID/GID 26 and RuntimeDefault seccomp are explicit.

`apply-databases.py network` creates only three DEV Namespaces, their database
NetworkPolicies and an additive operator egress policy. It never rewrites the
identity namespace's policy or identity cluster. Each namespace phase creates
its own cluster. Apply checks the live Kubernetes UID, three Ready nodes,
three Ready identity database instances, pinned image and owned app PVs.
It refuses ownership collisions, uses server dry-run and server-side apply
without force-conflicts, then reads definitions back.

These are dedicated DEV bootstrap operations, not a bypass of the full
dev/prod release-environment destination checks. ArgoCD applications and full
site configuration are still separate deployment work.

## Actual Deployment: 2026-09-11

Before creating database workloads, host PV inspection independently reverified
all three mounted filesystems and prepared directories. Namespaces/policies
were applied first. HeteroCloud, Flow and Syouyu clusters were then created and
verified sequentially, avoiding nine simultaneous initializations.

All nine instances became Ready. In every namespace:

- `dev-postgres-1` was primary on `hetero-dev-1`.
- `dev-postgres-2` and `dev-postgres-3` ran on the corresponding DEV guests.
- Each PVC was Bound to its pre-reserved app PV, not an identity volume.
- Read-only SQL reported `synchronous_commit=on` on all instances.
- Primary reported two `streaming` replicas with `sync_state=quorum` and
  `synchronous_standby_names` beginning with `ANY 1 (`.
- Recovery flags matched the primary/standby roles.

`verify-databases.py NAMESPACE` performs those placement, PVC and SQL checks.
It does not create test data, kill a pod or claim write-recovery verification.

All four apply phases were repeated successfully. Comparing the nine database
Pod UIDs, container IDs and restart counters before/after confirmed they did
not change. The identity cluster remained three Ready instances at every apply
and verification gate. No existing service restart or guest reboot was issued.

## Transport Verification: 2026-09-11

After checking DEV1 machine identity and the live Kubernetes UID, read-only
probes verified all three database services at
`dev-postgres-rw.<namespace>.svc.cluster.local:5432`. Each namespace has its own
distinct CA. OpenSSL PostgreSQL STARTTLS from the existing `dev-postgres-1`
container succeeded with the correct CA and matching service hostname. The
other namespace's CA and a mismatched hostname were both rejected with a
certificate-verification error. All nine cases passed.

The procedure is retained as `verify-tls.py`. It passes only public CA bytes
through stdin; it creates no Pod, writes no database records and does not
restart workloads. This verifies transport from a database Pod, not access from
application Pods under their NetworkPolicies, SQLx behavior or password login.
Those application-level checks remain necessary.
