# Fresh DEV Native Bootstrap

`scripts/bootstrap-dev-guest.py` prepares private guest payloads locally. Its
separate `install` and `start` commands run only when explicitly invoked on the
matching fresh guest. Nothing calls SSH, libvirt, Kubernetes or a remote command
endpoint. This tooling has not been deployed or exercised on real guests.

## Fixed Boundary

- Exactly `hetero-dev-1`, `hetero-dev-2`, `hetero-dev-3`, using Curie's allocation
  in `deploy/dev/libvirt/profile.json`: `dev0`, `172.28.240.11` through `.13`.
- Pin each expected libvirt/DMI UUID and independently observed, distinct
  `/etc/machine-id`. The installer checks hostname, both identities and `dev0`.
  It never rewrites a machine ID, hostname, network profile or existing state.
- Fresh issuer generated by the verified native `ipars init`; issuer key remains
  in the private operator staging directory, never in a guest payload. Each
  guest gets its own one-use, 24-hour enrollment token and random agent API token.
  CP, signal and STUN operator API tokens are separately generated.
- Only guest 1 runs the initial SQLite CP at `http://172.28.240.11:8443`, plus
  signal on private port 9443 and STUN on private UDP 3478/3479. This is **not CP
  HA**, and port 8443 does **not** imply TLS. Curie's private-network firewall is
  required; operator APIs must not be exposed to an untrusted network.
- VPN pool `10.251.0.0/24`, device `heteronetwork0`. Clear inherited daemon environment;
  pin dev CP/signal/STUN; disable public STUN fallback, public-service promotion,
  public web gateway and overlay services. Kubernetes/Docker discovery and route
  installation are not enabled. No public-service bootstrap helpers are installed.

## Provisioner Handoff

Curie owns VM/image/network creation and its SSH key contract. Do not modify an
existing production guest or reuse its credentials. Provisioning must supply an
inventory JSON with `schema_version: 1` and an ordered `guests` array. Each entry
has only `name`, `address`, `product_uuid`, and `machine_id`. UUIDs must match
Curie's deterministic libvirt allocation; machine IDs must be observed, not
guessed or copied from another machine. Resolve how the IDs are collected before
payload generation; this script does not circumvent guest administration to get
them.

The actual fresh-guest provisioning gives key-only `devadmin` temporary
`NOPASSWD: ALL` sudo access for bootstrap. This is full guest-root authority,
not a command-scoped grant. It is restricted operationally to these exclusive
dev VMs; the provisioner owns its later removal or restriction. This tool does
not create a cloud-init fragment or change sudoers, passwords or SSH policy.

The provisioner must independently place that node's complete payload at
`/opt/heteronetwork-dev-bootstrap`, owned by root, directory mode 0700, with the
supplied private file modes. A devadmin-writable directory is intentionally
rejected. The large native archive is a separate file, not embedded in user-data.
Do not transfer `issuer.key`, another node's directory, or the top-level staging
directory. Seed media/backing storage containing these fresh credentials must
also remain private. Released daemon flags have been reviewed; this does not
replace live enrollment and connectivity validation.

## Local Preparation

Use the already verified/published dev release artifact and archive. Do not
download again merely to stage; do not change channel selections.

```sh
python3 scripts/bootstrap-dev-guest.py stage \
  --artifact /private/heteronetwork-release-artifact.json \
  --archive /private/heteronetwork-dev-linux-amd64.tar.gz \
  --inventory /private/observed-dev-guests.json \
  --output /private/fresh-dev-bootstrap
```

The existing native release validator checks the artifact schema and source
repository. This bootstrap consumes only the base archive: it does not verify,
retain or install the bound sudo companion and reports
`verification_scope: base_archive_only`, `sudo_companion_verified: false` and
`sudo_installed: false`. It is not a full native-stage preparation; that separate
workflow requires `--sudo-archive`. No sudo capability readiness is claimed.
The base archive SHA-256 and every member digest are verified before any
binary execution; traversal, links, non-ELF binaries and oversized archives are
rejected by the existing extractor. Only the verified CLI is executed locally
to generate credentials, never with `--spawn-daemons`. Synthetic test hashes are
not valid operational inputs. Output and all ancestors must have trusted owners
and no group/other write access. The output directory must not already exist.

Each payload includes `INSTRUCTIONS.txt`. Install guest 1 first, then explicitly
start it; start guests 2/3 after the CP is healthy. Required guest packages are
Python 3, iproute2, iputils ping, curl, systemd and WireGuard tools/support.
The explicit `prerequisites` command below can install the fixed OS packages;
`install` and `start` never install packages implicitly.

## Explicit OS Prerequisites

On the identity-matching fresh guest, before `install`, run the reviewed helper:

```sh
sudo /usr/bin/python3 /opt/heteronetwork-dev-bootstrap/bootstrap-dev-guest.py prerequisites \
  --bundle /opt/heteronetwork-dev-bootstrap
```

This root-only command reuses bundle privacy, guest UUID/machine-ID/hostname/dev0
and dev-artifact checks, verifies generated file hashes and the base archive
digest, and refuses existing HN config, state, journal or units. It serializes
prerequisite invocations by locking the bundle directory without writing it.
Python 3 and `ip` must already exist to perform these checks. Only Debian/Ubuntu
are accepted, using the fresh image's administrator-controlled distro apt
configuration. No repository, signing key, sudoers or network configuration is
added; inherited proxy/apt environment is cleared.

The fixed packages are `python3`, `iproute2`, `iputils-ping`, `curl`, `systemd`
and `wireguard-tools`. Apt metadata update must succeed; installation uses
`--no-install-recommends --no-upgrade`, with bounded lock/network/process waits.
There is no arbitrary package, URL or command parameter. Apt dependencies and
normal package maintainer scripts still run as root. Existing installed target
packages are not upgraded. A successful `wg --version` is checked afterward;
this does not prove kernel WireGuard support or VPN health.

Repeat before HN installation to recover an interrupted apt operation; no
credentials are regenerated and no journal/reset operation is performed. Apt
can leave partial package state on failure or timeout: inspect that state and
any surviving package-manager lock before retrying, never delete its lock files.
No HN service is started. After HN installation this fresh-only command refuses.

## Journal and Failure

Install refuses existing HeteroNetwork config/state and units. Inside the pinned
fresh dev VM it uses the conventional `/etc/heteronetwork`,
`/var/lib/heteronetwork`, `/opt/heteronetwork/bin` and
`heteronetwork-agent.service`, compatible with the Kubernetes helper's hardcoded
paths. Guest 1 also gets `heteronetwork-control-plane.service`,
`heteronetwork-signal.service` and `heteronetwork-stun.service`. Isolation comes
from exclusive guest identities and fresh credentials, not renamed units.
The agent token is `/etc/heteronetwork/kubernetes/agent-api-token`, root-owned
mode 0400, matching the helper. Installation also creates a private
`/var/lib/heteronetwork-dev-bootstrap` journal with an exclusive process lock.
The journal binds the node, cluster, immutable artifact and generated file hashes.
Existing different files, links or ownership never get overwritten.

Completed installation is idempotent for the same bundle. Interrupted installation
can continue only where existing bytes/modes match exactly; a partial extraction
or partial file may require reviewed recovery. Keep the journal and partial tree;
there is no forced reset or automatic removal. Failed local preparation similarly
leaves its exclusive output directory and never silently regenerates keys there.

Start waits at most 60 seconds for the pinned dev CP health endpoint without
proxies or redirects. It writes `enrolling` before the one-shot registration;
timeout/failure/crash leaves that phase and refuses automatic retries. Investigate
the CP token consumption and local state before any manual recovery. Never remove
the agent identity or replay a one-use token to make a failed bootstrap pass.
After registration, normal agent service startup uses persisted state without
the join token. Repeating a completed start does not restart an already-active
systemd unit. No rollback stops unrelated services or deletes databases.

The phases are `installing`, `installed`, `enrolling`, `enrolled`, `started`,
then optionally `vpn-verified-local`. `start` reports `vpn_verified: false` and
`kubernetes_ready: false`; systemd startup is not a readiness claim.

## VPN Gate Before Kubernetes

After all three agents have enrolled, independently collect their public node
IDs, assigned VPN addresses and WireGuard public keys. Do not assume allocation
order. Place a root-owned private roster file on each matching guest:

```json
{
  "schema_version": 1,
  "cluster_id": "<fresh-cluster-id>",
  "nodes": [
    {"name": "hetero-dev-1", "node_id": "<observed>", "vpn_ip": "<observed-10.251-address>", "wireguard_public_key": "<observed-base64-public-key>"},
    {"name": "hetero-dev-2", "node_id": "<observed>", "vpn_ip": "<observed-10.251-address>", "wireguard_public_key": "<observed-base64-public-key>"},
    {"name": "hetero-dev-3", "node_id": "<observed>", "vpn_ip": "<observed-10.251-address>", "wireguard_public_key": "<observed-base64-public-key>"}
  ]
}
```

On each guest, explicitly run:

```sh
sudo /usr/bin/python3 /opt/heteronetwork-dev-bootstrap/bootstrap-dev-guest.py verify-vpn \
  --bundle /opt/heteronetwork-dev-bootstrap --roster /root/dev-vpn-roster.json
```

This gate takes 13 samples over at least 60 seconds: CP and authenticated agent
health, pinned local identity, exactly the two expected WireGuard peers, routes
through `heteronetwork0`, interface-bound pings, recent handshakes, and increasing
encrypted RX/TX counters for both peers. It reads no WireGuard private keys.
A failed recheck invalidates previous local evidence. Repeating `start` also
requires fresh verification.

The deployment owner must collect passing reports from **all three** guests with
the same cluster and roster digest, checked within the preceding five minutes,
before proceeding. One report is not cluster readiness. These reports establish
all six directed peer paths; they still report `kubernetes_ready: false`.

### Kubernetes Helper Blocker

Do **not** run the released dev4 `kubeadm-ha-node.sh prepare` yet. Its `prepare_host`
unconditionally calls `install_public_services_bootstrap_autopilot`, which
installs/enables the public-services bootstrap timer without a disable override.
It also expects a relative `../deploy/systemd` tree not shipped alongside native
libexec helpers, so failure can occur after host preparation has already mutated
the guest. The helper owner must provide and verify an explicit supported
no-autopromotion path before actual Kubernetes bootstrap. This installer does
not install or invoke that helper to bypass the blocker.

The source-only `fresh-dev` profile now supplies that path; see
[KUBERNETES.md](KUBERNETES.md) for dependencies, explicit configuration and release
delivery requirements. It does not change the verified dev4 archive.

Once that prerequisite is resolved, Kubernetes preparation must follow the
three-guest VPN gate, use observed `10.251.0.0/24` node/backend addresses, and
explicitly override the helper's defaults to dev pod CIDR `172.29.0.0/16` and
service CIDR `172.30.0.0/16`. Dev API/DNS names and split-DNS prerequisites also
need explicit configuration: initial enrollment disables overlay services.
Never reuse production credentials, discovery endpoints or autopromotion.
